# Karpathy 스타일 작업 원칙

> 출처 고지: multica-ai/andrej-karpathy-skills 원본을 이 세션에서 직접 가져올 수 없어(GitHub 접근 범위 제한),
> Andrej Karpathy가 공개적으로 밝혀온 코딩 철학(nanoGPT/minGPT 스타일, 블로그·강연 발언)을 근거로
> 이 프로젝트에 맞게 재구성한 버전이다. 원본 레포 확보 시 이 파일을 교체한다.

## 핵심 태도

1. **이해가 먼저, 코드는 나중**. 문제를 완전히 이해하기 전에 파일을 열어 고치지 않는다.
   세션 첫 응답은 항상 이 순서: ①현재 상태 파악 ②이번 세션의 단일 목표 정의 ③가장 단순한 경로 제시.
2. **읽기 쉬움이 영리함을 이긴다**. 한 번에 이해되는 50줄이 "우아하지만" 두 번 읽어야 하는 20줄보다 낫다.
3. **추상화는 3회 반복 후에만**. 패턴이 세 번째로 나타나기 전까지 헬퍼·인터페이스·설정 옵션을 만들지 않는다.
   두 번째 반복까지는 중복을 허용한다 — 이르게 뽑은 추상화는 나중에 잘못된 방향으로 굳는다.
4. **끝까지 도는 것 하나가 부분적으로 도는 열 개보다 낫다**. 스캐폴드를 넓게 벌리지 말고,
   한 경로를 입력부터 출력까지 실제로 동작하게 만든 뒤 넓힌다 (이 프로젝트에서 이미 적용한 순서:
   히어로 → 체크인 → 다이어리, 각각 실제로 렌더/동작 확인 후 다음으로).
5. **삭제도 진행이다**. 안 쓰는 코드·죽은 분기·미완성 절반짜리 기능은 있으면 있을수록 다음 사람(미래의 나)의
   이해 비용을 올린다. 남겨두지 말고 지운다.
6. **직접 실행해서 확인**. 타입체크·빌드 통과는 정확성 증거이지 기능 증거가 아니다. 가능하면 실제로 브라우저에서
   눌러보고 스크린샷으로 확인한다 (이 프로젝트의 `verify`/`run` 스킬, 헤드리스 브라우저 검증 관행 유지).

## 이 프로젝트에서의 적용

- CLAUDE.md 원칙("추측 금지. 설명 금지. 직설적으로 실행 가능하게")과 겹친다 — 같은 태도의 다른 표현.
- WORKFLOW.md §2.1의 "세션 시작 프로토콜"은 이 스킬이 상시 로드되어 있다는 전제로 쓰였다.
- plan 모드 진입 전 이 원칙으로 스코프를 먼저 좁힌다: "이번 세션에서 딱 하나, 가장 단순하게 도는 걸 만든다면 무엇인가?"
